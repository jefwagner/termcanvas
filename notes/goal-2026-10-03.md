## Milestone 2 — termviewer (CLI spec, finalized)

`termviewer` is a **CLI utility, not a TUI app**: no alternate screen, no raw
mode, no event handling, no key-to-quit. It prints exactly one clean,
self-contained frame and exits. It does **not** depend on `termcanvas-loop`.
It must work both written to a terminal and piped to a file:
`termviewer <pic_file> > file.txt` produces a file that a text editor with
ANSI support renders as the image.

### CLI shape

    termviewer [OPTIONS] <pic_file>

- **clap** for argument parsing.
- `<pic_file>` — the image to display. The `image` format-decoder features are
  a real (non-dev) dependency of this crate; decoders stay **dev-only** in
  `termcanvas` itself.
- `-w/--width <px>` — target width in pixels (1 px = 1 char column).
- `-h/--height <px>` — target height in pixels (1 char row = 2 px; an odd
  value is silently bumped up to the next even number).
- `-c/--crop <x,y,w,h>` — crop window in source-image pixels.
- There is deliberately **no aspect-ratio option** in this implementation.

### Sizing semantics

There is always a *target box*; the image is scaled, preserving its own aspect
ratio, to **fit inside** the box. No distortion; cells the image doesn't cover
are simply not drawn, so there is no letterboxing or centering logic. Output
is left-aligned — if the image is narrower than the box, the leftover right
columns stay untouched.

- Default box: terminal width × 2·(terminal height − 1). The height − 1
  reserves the last line for the shell prompt.
- If the image is smaller than the box, it is shown without scaling.
- `-w`/`-h` shrink the box in that dimension. When explicitly given they are
  **exact**: the canvas is that size, and the image is **upscaled** if needed
  to fill it (explicit size overrides the no-upscale default).
- **stdout not a tty** (e.g. `> file.txt`): there is no terminal size, so
  both `-w` and `-h` are **required**; missing either is a usage error.
  Detect with `std::io::IsTerminal`.

### Crop semantics

`-c/--crop x,y,w,h` is defined on the **unscaled** source image, clamped to
image bounds. Pipeline order is fixed: **load → crop → scale-to-box**.
Scaling happens after cropping, never before.

### Output hygiene

Exactly one frame: cursor home → full frame → trailing newline. No
`Clear(All)`, no cursor hide/show, no reset-position litter beyond the frame
itself, and **no key-wait of any kind** — waiting on stdin would hang piped
runs. The reserved bottom line is for the shell prompt.

## Milestone 3 — termcanvas-loop v0

New crate `crates/termcanvas-loop`. Distill, don't invent — the starting point
is the loop in `examples/snake.rs`: poll-with-deadline input, tick pacing,
header/canvas drawing, terminal setup/teardown.

Public shape (agreed with jef):

- The loop crate owns the terminal lifecycle: raw mode, cursor visibility,
  alternate-screen setup/restore, panic/error-path restoration. Apps never
  touch global terminal state.
- Apps implement a trait, roughly:

  ```rust
  trait App {
      fn init(&mut self, ctx: &LoopCtx) -> Result<()>;
      fn handle_event(&mut self, ev: Event, ctx: &LoopCtx) -> Result<Flow>;
      fn tick(&mut self, dt: Duration, ctx: &LoopCtx) -> Result<Flow>;
      fn draw(&mut self, canvas: &mut TerminalCanvas, ctx: &LoopCtx) -> Result<()>;
  }
  ```

  (`Flow`: continue vs. exit; `LoopCtx`: whatever scoped context the loop
  provides — terminal size, the canvas' `CharRect`, etc. Exact names and
  details are the implementer's job; this is the agreed shape.)
- The app draws into whatever `CharRect` the loop gives it — never a hardcoded
  full-terminal rect.
- Input reaches the app via the loop's event dispatch, so a future host
  (arcade) can filter or reroute events.
- Resize handling: at minimum, the loop reports resize events to the app;
  rebuilding buffers on resize is acceptable v0 behavior.
- Doctests on public items wherever behavior is demonstrable headless; render
  correctness beyond buffer arithmetic is verified by example run by jef after
  the run — flag this in the summary, don't claim test coverage for it.

## Milestone 4 — termsnake

New crate `crates/termsnake`, **lib + bin**:

- All game logic lives in the library target: a `SnakeApp` type implementing
  the loop crate's `App` trait. Game state, tick logic, colors, scoring move
  from `examples/snake.rs` essentially unchanged where possible.
- `main.rs` is a thin wrapper (~20 lines): build `SnakeApp`, hand it to the
  loop's run function, propagate errors.
- Arcade-readiness rules (these are the point of the lib/bin split):
  - `SnakeApp` owns no global terminal state — the loop does.
  - It draws into the loop-provided `CharRect`, sized at runtime.
  - All input flows through the loop's event dispatch.
  - No logic that only makes sense in a standalone binary lives in the lib.
- Delete `examples/snake.rs` as part of promotion; remove `rand` from
  dev-dependencies and put it in this crate's real dependencies.
- Score header and game-over screen carry over, drawn via the App/ctx shape.
